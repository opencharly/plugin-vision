# 2026.259.2330 — feat(vision): the `vision:` check verb

Adds the `vision` check verb: validate an IMAGE (a screenshot a check just
produced) by sending it directly to an OpenAI-compatible vision endpoint.

## Why

A screenshot produced by `wl:` / `vnc:` / `cdp:` / `spice: screenshot` is a file
on the host, and "does this screenshot show the new layout / the right color /
the expected state" is not an assertion a shell command can express. This verb
reads that file, sends it as a base64 data URL (ollama's OpenAI layer accepts
base64 data URLs ONLY — remote image URLs are unsupported), and grades the
model's reply with the shared matcher/verdict pipeline, so a `check:` step can
assert on an image exactly like any other verb.

## What

- `schema/vision.cue` — `#VisionInput` (the verb's own authoring contract) plus a
  SANCTIONED mirror of `spec/schema/llm.cue`'s `#LLMSpec`/`#LLMParams` and their
  companions. The mirror exists so this plugin's schema compiles STANDALONE (the
  SDK compiles it serve-side; `cue exp gengotypes` reads it) while spec's defs
  generate Go — the shipped precedent is `plugin-desktop-kind`'s
  `schema/desktop.cue`. A parity test makes the next drift fail next to the fix.
- `params/cue_types_gen.go` — generated by `cue exp gengotypes` (+ the schemagen
  retag), reproducible.
- `provider.go` — decodes the op + typed input, enforces the required fields
  (prompt, artifact), bridges the plugin's params to the contract `spec` types,
  and returns `sdk.VerbVerdict` so the shared stdout/stderr/exit_status matchers
  and the artifact validators apply exactly as for any verb.
- `methods.go` — reads the image(s) into data URLs, and asserts the reply with
  `expect:` (contains / matches / not_contains), naming the model's actual answer
  on failure.
- `plugin.go` / `cmd/serve/main.go` — `verb:vision` + the served `#VisionInput`,
  dual-placement (in-process or out-of-process) by construction.
- The model call is the SDK's shared `llmkit.ChatVision` (R3): the SAME client
  the pipeline engine's agent stages use, so both speak the endpoint identically
  (idle bound, no env bleed, reasoning capture, vision content parts).

## Endpoint configuration

The step's `llm:` block reuses the shared `#LLMSpec`/`#LLMParams` vocabulary.
Resolution is field-wise: `EVAL_LLM_*` env > the step's `llm:` block > the
built-in local-ollama default.

## Verification

Unit + mock (hermetic): the full dispatch path (decode → read image → call →
verdict), the `expect:` assertion passing and failing with the model's reply in
the message, the regex/negative forms, the required-field failures, the shared
`stdout:` matcher grading the reply, mime inference, the multi-image form, and
the schema-parity check (mutation-verified: dropping a mirrored field reds it).

Live (R10), against the real local ollama vision endpoint with real generated
images:

```
$ go test -run TestLive -v ./...
--- PASS: TestLive_VisionAssertionAgainstRealEndpoint
    LIVE VERDICT: pass — the model identified the green image; reply=Green
--- PASS: TestLive_WrongExpectationFails
    LIVE VERDICT: fail (as authored) — the assertion gated the verdict;
      message=vision: assert: exit=1, want 0 (stderr: vision assertion failed:
      the reply does not contain "blue" (reply: Green))
```
